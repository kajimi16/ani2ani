# HITSZ 校园网 P2P 观影方案 — 实测调研（2026-11-02）

结论先说：**免客户端的浏览器方案在这套校园网条件下成立**。本机以 3 个独立浏览器进程实测，
稳态 P2P 分流 **66.7%**，与 N=3 时的理论上限 `(N-1)/N = 66.7%` 完全重合；服务端出口与播放器
自报字节双口径偏差 **3.1%**（同机 loopback 对照组 0.0%），即每一片只从源服务器取一次，
其余全部经 WebRTC 由观众互传。

测量对象、判据、排除的实验坑与容量推演均在下文，所有数字来自 `rounds/lan-r1/` 与
`rounds/local-r1/` 的原始产物。

---

## 1. 现场网络事实

| 事实 | 来源 | 对本方案的含义 |
|---|---|---|
| 全校 SSID 统一为 `hitsz`，观众分散在各楼 | 用户陈述 | 属于「跨子网」场景，非单 AP 场景 |
| 同 AP 下客户端隔离**不存在**（互 ping 通、WebRTC 可连） | 用户实测（测试 A） | 同区域观众可直连互传 |
| 跨楼可达：不同内网段互 ping / 互 HTTP 通 | 用户实测（测试 B） | 分片流量不出校园骨干，核心网带宽远大于服务器上行 |
| 本机网卡 `enp7s0` = `10.249.x.x/21`，另有 VPN 隧道 `28.0.0.1/30` | `ip -4 addr` | 服务必须绑定并对外公布**校园网卡地址**，不能公布 VPN 地址 |
| 校内 STUN 实际生效：1898 次 Binding 请求，其中 825 次来自校园网地址 | `/api/health` 的 `stun.requests` | 见 §5 的 mDNS 问题，校内 STUN 是跨子网直连的必要件 |
| 宿主机防火墙**已确证不拦截** | `ufw` 不活动；`iptables -S INPUT` = `-P INPUT ACCEPT`、零规则；`inet filter` 表未加载；`rp_filter=2`（loose） | 8080/TCP 与 3478/UDP 对校园设备可达。但自检仍是 loopback，校园网 ACL 与 WebRTC 实际连通仍需手机实测一次 |

## 2. 栈组成（全部用户态，无 sudo、无特权端口）

```
ffmpeg ──HLS(.m3u8 + .ts)──▶ Caddy :8080 ──┬─▶ 观众浏览器（hls.js + p2p-media-loader）
                                            │        │  WebRTC DataChannel 互传分片
                                            │        ▼
                                            └─▶ node :8001 ── WebTorrent tracker（/tracker, WS）
                                                     └──── STUN udp/3478（校内自建）
```

- **Caddy**：静态托管 + Range + 逐请求 `size` 计账（JSON 访问日志）。选 Caddy 而非 nginx，
  是因为它单文件、无官方静态二进制以外的构建依赖，配置里天然支持 `handle_path` 与 WS 反代。
- **tracker**：`bittorrent-tracker`（纯 JS，WS `noServer` 模式挂在同一 node 进程上，由 Caddy 反代）。
- **STUN**：自写 76 行 RFC 5389 binding server，只回 `XOR-MAPPED-ADDRESS`，不中继媒体。
- **播放器**：`hls.js 1.7.4` + `p2p-media-loader-hlsjs 4.0.0`，esbuild 打成单文件 730 KB。

## 3. 测量方法

判定不看「看起来流畅」，只看可复算的数：

1. **播放器侧**：`onChunkDownloaded` 按 `downloadSource` 累计 `downP2P` / `downHTTP`，
   `onChunkUploaded` 累计 `upP2P`，每秒 `POST /api/report`（累计值，丢包无害）。
2. **服务端侧**：Caddy 访问日志的每条 `/hls/*` 响应 `size` 字段，按响应完成时刻落入窗口求和。
3. **判定**：`scripts/verify-round.sh` 取稳态窗口 T+60s…T+180s（冷启动 0–30s 不参与），
   计算 P2P 占比、活跃客户端数 N、理论上限与双口径偏差。

### 3.1 判据的数学修正（重要）

原方案定的「稳态 P2P ≥ 70%」在 N=3 时**数学上不可达**：同步观影下每一片至少要有一个观众
从源站取回，因此服务端份额 `≥ 1/N`，P2P 上限 `≤ (N-1)/N = 66.7%`。固定 70% 会把完美实现判成失败。

改为随 N 变化、并给出上限的双判据：

$$
\text{required}(N) = 0.85 \times \frac{N-1}{N},\qquad
\text{verdict} = \left[\ \text{ratio} \ge \text{required}(N)\ \right]
$$

N=3 → 56.7%；N=4 → 63.8%；N=10 → 76.5%；N=200 → 84.6%。报告同时给出实测 ratio 与
`(N-1)/N` 上限，实测可超过该"上限"（迟到观众可从已有分片的观众取首片，源站取回次数少于 1× 码流），
所以该上限是保守门限而非硬顶。

### 3.2 双口径交叉验证

播放器自报的 `downHTTP` 与 Caddy 记账在同一窗口内比对，偏差超过 `max(10%, 单分片占比)` 时
判定「统计不可信」，该轮**不计入调参轮次**，先修埋点。这条规则确实拦下过真实错误（见 §6.1、§6.2）。

### 3.3 播放头断言（防止「健康数字、实际卡死」）

单看字节比例会被骗：预取也算下载，一条卡住的播放可能拉满流量并给出漂亮的 P2P 占比。
因此 `verify-round.sh` 额外断言**实际解码秒数**：稳态窗口内 `playedSec` 增量必须 ≥ 墙钟的 50%，
否则判「无效测量」（退出码 2，不计轮次）。用单调累加器而非 `videoTime`，是因为共享时钟会让
`videoTime` 每圈归零（见 §6.1）。

这条断言不是理论洁癖，它在开发中真的拦下了一轮：某次编辑误删了 `snapshot()` 里的
`videoTime`/`buffered` 字段，服务端收到的永远是 0，round 的字节比看起来完全正常（83.8%），
但播放头增量为 0 —— 只有断言把它判为无效，否则就会当成「已达成」写进结论。

**证据等级必须和数字一起读**（`verify-round.sh` 的 `evidence` 行）：

- 上表前 8 轮全部是**同一台机器上的浏览器进程**，没有无线链路、没有 AP、没有校园骨干。
  它们走 `127.0.0.1` 或本机校园 IP，都是本机投递。按现在的分类应为 `all-local`；
  这些轮次录制于 addr 字段引入之前，脚本如实报告 `unrecorded`，**不猜测**。
  它们的用途是**验证实现与埋点**（协议是否打通、参数是否合理、测量是否可信），
  **不是**给出放映现场的分流率。
- `mixedcheck` 含 2 台真手机（`10.250.x.x`、`10.250.1.x`）与 1 个主机浏览器，
  被判为 `MIXED` —— 同样不能单独作为现场证据。

因此「放映现场能达到多少 P2P」这一项目前**仍是空白**，需要一轮 `evidence: network-only` 的真实设备轮来填。
本报告的容量推演（§7）用的是这些轮次的**结构性结论**（源站 ≈ 1 × 码流、上行守恒），
这类结论与链路类型无关；而具体百分比一律以上表证据等级为准。

这些轮次的播放头推进均为墙钟的 100%（`playhead (legacy)` / `played` 行），即测的是播放而非纯预取。
`default-n6` 是最终默认配置（不带 URL 参数）的验证轮。

`lan-r2` 逐观众明细（稳态 120s 窗口，最终版本）：

| 观众 | P2P 下行 | HTTP 下行 | 上行贡献 | 分片 P2P/HTTP | 连接数 | 播放位置 |
|---|---|---|---|---|---|---|
| d3a6 | 25.54 MB | 15.07 MB | 30.14 MB | 19 / 11 | 2 | 172.9 s |
| 08c9 | 31.06 MB | 9.56 MB | 19.11 MB | 23 / 7 | 2 | 172.9 s |

90 次分片获取中 30 次来自源站（正好 1/N）。三人播放位置一致（172.9 s），即放映会的同步场景。

## 5. 两个只在真实浏览器里才暴露的坑

### 5.1 Chrome 的 mDNS 隐藏本地 IP → 跨子网必须靠 srflx

Chrome 默认把 ICE host 候选里的内网地址替换成 `xxx.local`（mDNS 主机名），而 mDNS 只在同一广播域
内可解析。HITSZ 观众分散在不同子网，因此**仅靠 host 候选无法直连**。解法是把 STUN 放在校内：
观众拿到的 `srflx` 候选就是自己那张校园网卡地址，对方可直接路由到。

实测：1898 次 Binding 请求，其中 825 次来自 `10.249.x.x`，说明播放器确实在用它，
且局域网轮与 loopback 轮都建起了 DataChannel（每台 `peers=2`）。

为避免「进程活着但 STUN 逻辑写错」这种沉默失败，`check-stack.sh` 现在主动发一个 RFC 5389
Binding 请求，核对响应类型、magic cookie、transaction id 回显，以及 `XOR-MAPPED-ADDRESS`
里的端口是否等于自身源端口（已用错误端口做负向验证：断言会失败并退出 1）。

### 5.2 预取窗口是这套方案的第一个真实陷阱

`p2p-media-loader` 的默认窗口是 `httpDownloadTimeWindow: 3000s`、`p2pDownloadTimeWindow: 6000s`
（面向直播/自适应清单）。在 4 分钟 VOD 清单上，它们等价于「把整条流整个预取」：

- 默认值实测：每个观众在 6 秒内拉下 **75.7 MB**（≈ 整条流），三个进程数字完全相同，
  播放头卡在 5.9 s —— 带宽全用在预取上，播放反而停住。
- 反向踩坑：把 HTTP 窗口压到 10 s、P2P 窗口 60 s，则「邻居供不上 + 自己也不许走 HTTP」，
  2/3 观众冻在 4.0 s，源站 54 MB 全喂给一个观众，累计 ratio 掉到 28.5%。

可用值：`httpDownloadTimeWindow: 60`、`p2pDownloadTimeWindow: 120`，
配合 `maxBufferLength: 20` / `maxMaxBufferLength: 40`。教训写进部署方案：**HTTP 窗口不可低于
约两个分片窗口的余量**，它是 P2P 失败时唯一的兜底路径。

### 5.3 应急回退开关 `?p2p=off`（已实测）

同一页面加参数即关闭 P2P、回到纯 HLS 模式，用于「校网中途封锁 WebRTC」这类事故。
实测该模式下 `peers=0`、播放正常推进（4.9 s），且 HUD 仍能显示服务端字节
（8.04 MB 累计）—— 因为 P2P 引擎不参与加载时其回调不会触发，必须另用 `FRAG_LOADED`
补记 HTTP 字节，否则中控台会看到「0 MiB 服务器」的假象。

### 5.4 领播偏移（lead/follow）：实测证明默认不该开

同步观影下「全员同一瞬间要同一片、彼此都没有」看似是这套方案的结构性风险，直觉对策是让少数观众
加深预取（lead 缓冲 90 s、follow 20 s），由 lead 替全群回源。**实测否掉了这个直觉。**

先看基线（N=6，全员 follow，库的 `highDemandTimeWindow` 自行调度）每个观众的回源分片占比：

| 轮次 | 角色 | 各客户端回源分片占比 | 最大/公平份额 | ratio | 源站字节 |
|---|---|---|---|---|---|
| `follow-n6` | 全员 follow | 15.2 / 6.1 / 18.2 / 21.2 / 15.2 / 24.2 % | **1.45×** | 83.1% | 44.73 MB |
| `lead1-n6` | 1 lead + 5 follow | **75.0** / 3.6 / 3.6 / 7.1 / 7.1 / 3.6 % | **4.50×** | 84.7% | 37.75 MB |

结论与直觉相反：

1. **库本身已经在做分片级分摊**。全 follow 时没有任何 peer 吃掉全部回源，最坏也只有公平份额的
   1.45 倍；N=3 轮同样是 11/10/9 的近似均匀。
2. **加 lead 是把压力集中，不是消除压力**。1 台 lead 独占 75% 回源，上行 132.2 MB/120 s（≈8.8 Mbps），
   其余 5 台只有 8.3–30.8 MB（3.78× 公平份额）。换来的 ratio 增益仅 +1.6pp、源站字节 −15%。
3. **在 WiFi 上这个交换是亏的**：每台上行才是稀缺资源，被集中的那台正是最可能先卡的机器。

因此**默认改为全员 follow**，`?role=lead` 仅在下列条件下才用：`verify-round.sh` 实测回源分布
`worst/fair > 2.0`（退化到单 peer 承担源站流量）时，把**有线口、上行最好**的一台指定为 lead，
好过让随机一台成为受害者。这条判据已做成脚本输出的一部分：

```
origin spread    worst 8/33 = 1.45x fair (limit 2.0x) — balanced — ...
origin spread    worst 21/28 = 4.50x fair (limit 2.0x) — concentrated — ...
```

另：早期用 peerId 哈希自动抽签分配角色，实测出现过 6 台里 5 台都是 lead（哈希 mod 5 恰全为 0，
约 1/600）。自动抽签已移除 —— 角色必须是显式运营决策，不能交给概率。

### 5.5 跨子网、跨设备 WebRTC 已实测打通（2 设备，非本机模拟）

前面所有轮次都是同一台机器上的浏览器进程。本次首次接入**真实手机**，两者分属不同子网：

| 设备 | 地址 | 与主机关系 |
|---|---|---|
| 主机（server） | `10.249.x.x/21` = `10.249.56.0/21` | 基准 |
| 手机 | `10.250.x.x` | **在该 /21 之外**，不同子网 |

STUN 计数确认手机确实在使用校内 STUN（285 次 Binding，来自 `10.250.x.x`），
且两端 `peers=1` —— srflx 候选配对成功，WebRTC DataChannel 建立。

窗口内传输（`rounds/real-n2/`）：

| 客户端 | peers | P2P 下行 | HTTP 下行 | P2P 上行 | 分片 P2P/HTTP |
|---|---|---|---|---|---|
| `3d00`（手机侧） | 1 | **13.94 MB** | **0.00 MB** | 0.00 MB | 10 / 0 |
| `c928`（主机侧） | 1 | 0.00 MB | 9.51 MB | **14.40 MB** | 0 / 7 |

手机侧的 10 个分片**全部**由对端经 WebRTC 取得，该窗口源站字节为 0；质量守恒闭合
（上行 14.40 MB ≈ 下行 13.94 MB）。这条实测把「跨楼 srflx 直连成功率」从「只有 ICMP/HTTP 层证据」
提升为「WebRTC 实际传输成功」。

**但该轮不可用于判据**：`verify-round.sh` 返回 `exit=2`（无效测量），两个原因都成立：

- N=2 < 3，判据阈值没有意义（N=2 的上限本身只有 50%）；
- 播放头在 119 s 墙钟内只推进 25 s（21%）—— 手机锁屏/切后台后被浏览器限流并停止上报。

后者是运营层的真实坑：**手机必须保持亮屏且在前台**，否则该观众既不再拉流、也不再播种。
iOS/Android 都会在锁屏后冻结页面定时器与网络活动。

### 5.6 共享播放时钟（「进网页就能一起看」的实现与实测）

原始需求是「用户只需要进入网页就能一起看」。此前实现没有共享时钟：页面加载即从 0 播放，
于是**只有所有人同一瞬间刷新才同步**，晚到者从 0 开始 —— 既看到不同画面，又需要一段
别人缓存里没有的分片，直接拉低 P2P 占比。实测中出现过 vt 66 / 147 / 184 同时存在的情形。

修法：服务端发布一个 epoch（`/api/health` 的 `sync.epochMs`，`POST /api/sync` 可改，
`/api/reset` 会把 epoch 重置为轮次起点），播放器按 `(now − epoch) mod duration` 求目标位置，
并在 `loadedmetadata` 立即 seek、之后每 5 s 检查一次漂移（阈值 3 s）。位置对时长取模，
使 600 s 测试片可循环支撑多轮而无需碰观众设备；`?sync=off` 退回旧行为。

实测（3 台本机浏览器，epoch 已设为 120 s 前）：

| 客户端 | 位置 | 漂移 | seek 次数 | 说明 |
|---|---|---|---|---|
| 早加入（9231/9232） | 168.46 s / 168.51 s | 0.2 s | 1 | 开机即对齐 |
| 22 s 后加入（9233） | 168.58 s | 0.2 s | 1 | **晚加入直接落到同帧** |
| 期望值 `(now−epoch) mod 600` | 168.81 s | — | — | 三者误差 ≤ 0.3 s |

`?sync=off` 验证：位置 13.67 s、`syncSeeks` 为空 —— 确认按旧行为从 0 起播。

这条改动同时改变了测量口径：此前的「同步」是靠同时启动近似出来的，现在是真的同一帧，
所以 P2P 占比测的是真实放映场景。`syncDrift` 也作为 gauge 上报，中控台可直接看出谁跑偏。

## 6. 测量埋点自身的缺陷（已修）

本轮实现共享播放时钟之后，连续暴露了 4 个会让「测量」说谎的问题。它们的共同特征是
**数字看起来很好，结论却是假的**，因此每一条都配了一个会让该轮直接判为无效测量的护栏。

### 6.0 判据护栏一览（`verify-round.sh`）

| 护栏 | 触发条件 | 为什么必须存在 |
|---|---|---|
| 成员判定 | 末条采样早于窗口结束 15 s，或窗口内 `downP2P + downHTTP == 0` | 挂着不干活的标签页仍在上报，会把 N 抬高 → 上限 `(N-1)/N` 跟着虚高。实测有一轮 N=6 里 3 台 0 字节（`sync-n3c`），修正后 N=3 |
| 播放进度 | 窗口内 `playedSec` 增量 < 墙钟 50% | 预取也会产生流量；播放头不动时字节比毫无意义 |
| 零回源 | 窗口内源站字节 = 0 且 P2P > 0 | `(N-1)/N` 的前提是「每个分片至少回源一次」。源站 0 字节说明 swarm 在窗口前已缓存整条流，`100% P2P` 是假象（见 §6.4） |
| 双口径偏差 | 播放器 HTTP 字节与 Caddy 记账偏差 > max(10%, 单分片占比) | 抓埋点错误；但低流量下采样离散化本身就有 1 个分片的误差，不能一律按百分比判死 |
| 来源分类 | 每条采样记录 `X-Forwarded-For`；脚本把**主机自身全部网卡地址**（`ip -4 -o addr show` 实时枚举）与 loopback 一并归为 local，其余为 network | 主机用校园网 IP 打开的浏览器仍是本机投递、没有无线链路，若只把 `127.*` 当本地就会把它误判成真实设备，护栏形同虚设。输出 `evidence` 行：`network-only` / `MIXED` / `all-local` / `unrecorded` |
| 回源集中度样本量 | 窗口内源站分片 < 20 时不判集中度 | 4 个分片摊到 3 台会算出 2.25×，纯噪声。样本不足时明确打印「too few to judge」 |
| 稳态窗口必须落在轮次内 | `measure-round.sh` 拒绝 `duration < 190 s`，并把窗口尾部 clamp 到实际结束 | 只跑 120 s 时窗口 T+60..180 会超出轮次结束 60 s，在线客户端全被判「窗口末离线」，好轮次被误判无效 |

### 6.1 播放进度不能用 `videoTime`

共享时钟按 `(now − epoch) mod duration` 定位，`videoTime` 因此每圈归零。原先「取 `max(videoTime)` 的增量」
的检查在回绕时读到 `+2s / 199s`，把一轮完全正常（100% realtime 播放）的轮判成无效。
改为播放器维护单调累加器 `playedSec`：只在连续前进时累加，seek 时重新取基准，
回绕与跳转都不会污染它。旧轮次没有该字段，脚本显式退回 `videoTime` 并标注「legacy」。

### 6.2 双口径偏差要容忍采样离散

`sync-n3` 判出 13.1% 偏差。逐请求核对后：窗口内只有 7 个分片请求，
播放器每秒采样、Caddy 按完成时刻记账，基线采样最多早一个周期 → 恰好差一个分片（1.44 MB）= 13%。
这不是埋点坏了，是粒度问题。改为 `limit = max(10%, 一个最大分片 / 总字节)`。
同时把 Caddy 侧统计限定为 `.ts`（排除 m3u8），与播放器 `downHTTP` 的语义对齐。

### 6.3b 来源分类：不许拿本机进程冒充现场数据

早期所有轮次都跑在同一台机器上，从数据里看不出哪个观众是本机浏览器、哪个是真实手机。
服务端现在记录每条上报的 `X-Forwarded-For`（Caddy 自动添加，socket 对端永远是代理），
`verify-round.sh` 据此把客户端分为 `loopback` / `network` / `未记录` 三类：

- 全部 loopback → 打印「no network bottleneck; not real-device evidence」；
- 混有两者 → 打印 `MIXED round`，明确标注不得作为真实设备证据（loopback 那部分没有无线瓶颈）；
- 早期轮次无该字段 → 打印「origin not recorded」，**不猜测**成 loopback 或 network。

这条是为了防止一种很自然的误用：拿 3 个本机标签页的 83% 去证明「放映现场能到 83%」。

分类必须包含**主机自己的校园网 IP**。第一版只把 `127.*` 当本地，于是主机上用
`http://10.249.x.x:8080/` 打开的浏览器被判成 `network`——但它走的是本机投递，没有无线、
没有 AP、也没有校园骨干。现按 `ip -4 -o addr show` 实时枚举主机全部 IPv4 地址（含 VPN 与
docker 网桥）归为 local，并已用 10 个用例单测（`10.249.x.x` / `28.0.0.1` / `172.17.0.1` /
`::ffff:10.249.x.x` → local；`10.250.*` / `192.168.*` → network；`unknown`/缺失 → unrecorded）。

实测 `mixedcheck`（2 台手机 + 1 个主机浏览器）输出：

```
origins          10.249.x.x×1, 10.250.1.x×1, 10.250.x.x×1
evidence         MIXED (1 local / 2 network) — ... do not cite as real-device evidence
origin spread    only 4 origin segment(s) — too few to judge concentration (need >= 20)
```

这轮比值 69.3% 虽过判据（exit 0），但 `evidence` 行明确标注它不能当现场数据。

### 6.4 loopback 无法产出有效稳态测量

`sync-n3c`（3 个本机浏览器，600 s 片源）报 **100% P2P、源站 0 字节**。查访问日志：
整轮窗口内 `.ts` 请求为 0，而轮次开始前的 40 s 内源站已发出 **1656 MB**（≈ 3 台 × 整条 195 MB 片源）。
loopback 没有带宽约束，swarm 在窗口开始前就把整条流缓存完了，窗口内自然全是 P2P 互传。

所以该轮的不是「分流很好」，而是「没有回源需求可分流」。已加零回源护栏。
**结论：可信的稳态数字只能来自真实网卡或真实设备轮**（`lan-r2` 66.7%、`default-n6` 83.3% 均属此类）。

### 6.5 更早修复的两处

1. **Caddy 日志字段用错**：早期按 `bytes_written` 求和，该字段在此配置下为 `null`，
   导致「服务端字节 = 0」而播放器侧非零 —— 正是 10% 偏差规则把它拦下的。
   实际字段是 `size`（响应体字节），且 `ts` 是浮点 epoch 秒而非 ISO 字符串。
2. **窗口基线缺失**：窗口起点早于第一条采样时，原实现返回空窗口（表现为「3 个客户端、0 字节」）。
   改为回退到最早一条采样做基线。

两者都会让「无效测量」伪装成「0% P2P」，是这套方案里最容易自欺的地方。

## 7. 容量推演（基于实测，不是估算表）

`lan-r2` 稳态实测：3 观众合计 8.12 Mbps，其中源站 2.71 Mbps，即**源站出口 ≈ 1 × 码流**
（配置码率 2.5 Mbps + 容器/清单开销）。每观众上行 ≈ 1.81 Mbps，来自 `(N-1)/N × 码流`
的质量守恒。

这些数字来自**本机进程**轮次（`evidence: unrecorded`/`all-local`）。引用时必须分清用途：

- **结构性结论可用**——「源站出口 ≈ 1 × 码流」「上行总量 = P2P 下行总量」来自协议本身与
  质量守恒，和链路是 loopback 还是 WiFi 无关；
- **绝对带宽数字不可外推**——本机没有无线瓶颈，实际 WiFi 上的分流率只会更低，不会更高。
  表格里的「每观众上行」「无线聚合需求」是按码率与守恒关系推的，不是实测的无线数字。

由此得到两条与直觉相反的结论：

1. **源站上行不再是瓶颈**。N 增长时分母变大：200 人、2.5 Mbps 时源站仍只需 ~2.5 Mbps 出口，
   而不是 500 Mbps。P2P 把「N × 码流」变成「1 × 码流 + N × 上行」。
2. **真正的瓶颈转移给每条观众上行与 AP 聚合能力**。200 人 × 2.5 Mbps ≈ 500 Mbps 的
   无线聚合需求必须由多 AP 或部分有线承担；单台 802.11ac AP 现实聚合只有 200–400 Mbps。
   因此调度策略应是「每 AP 只让少数设备大量播种」，而不是人人满速播种。

`default-n6`（最终默认配置）给了 N=6 的实测锚点：6 观众合计 16.25 Mbps，源站 2.71 Mbps，
即源站仍是 **1 × 码流**；每观众平均上行 ≈ 2.26 Mbps，单台最高 47.9 MB（≈3.2 Mbps）。
对照 `lead1-n6`：源站 2.52 Mbps 略低，但单台最高上行 132.2 MB（≈8.8 Mbps）—— 正是「集中」的代价。
两者都印证「源站出口不随 N 增长」，而默认配置把上行压力摊平到每台。

| 观众数 N | 源站出口（2.5 Mbps 码流） | 每观众平均上行 | 无线聚合需求 | 判据阈值 `0.85(N−1)/N` |
|---|---|---|---|---|
| 3 | 2.7 Mbps | 1.8 Mbps | 8.1 Mbps | 56.7% |
| 6（实测） | 2.5 Mbps | 2.1 Mbps | 16.5 Mbps | 70.8% |
| 20 | 2.7 Mbps | 2.4 Mbps | 54 Mbps | 80.8% |
| 50 | 2.7 Mbps | 2.45 Mbps | 135 Mbps | 83.3% |
| 200 | 2.7 Mbps | 2.49 Mbps | 541 Mbps | 84.6% |
| 300 | 2.7 Mbps | 2.49 Mbps | 812 Mbps | 84.7% |

压低码率同样成立：720p、1.2–1.8 Mbps 时上述聚合需求线性下降，动画画面损失可接受。

## 8. 未验证项（不要当成已证明）

- **真实设备**：主体轮次是同一台机器上的 3–6 个独立浏览器进程（隔离 profile、各自缓存）；
  另有 1 次真实手机跨子网接入（§5.5），验证了跨子网 WebRTC 实际传输，但**没有验证**真实 WiFi
  的双向吞吐、多设备同 AP 的信道竞争，也未完成 ≥3 台真实设备的可判定轮。
- **规模**：最大实测 N=6，且全部是本机进程。**现场（network-only）分流率仍是空白**；
  20 人以上的分流比例、swarm 连通率、tracker 压力（WS 广播）都未压测。
- **认证行为**：hitsz 的 portal 认证是否会在播放中途超时踢线，未测。若会踢，表现为全体掉线，
  属于灾难级风险，必须在真实轮里观察 3 小时以上。
- **跨子网 WebRTC**：已实测打通一次（§5.5，手机 `10.250.x.x` ↔ 主机 `10.249.x.x`，
  纯 P2P 传输 0 源站字节）。但只验证了 **1 台**跨子网设备，成功率随设备数与 AP 环境变化，未统计。
- **版权与合规**：仅校内非营利放映、实例不开放公网注册，片源不出校内。

## 9. 真实设备轮：最小操作步骤

在放映场地（或任意能连 hitsz 的位置）执行：

```bash
cd ani2ani
bash scripts/start.sh                  # 打印 campus 地址，例如 http://10.249.x.x:8080/
# 让每台设备（手机/笔记本）连 hitsz，浏览器打开该地址，点一次「开声音」
bash scripts/measure-round.sh real-r1 240   # 采样 4 分钟，产物落 rounds/real-r1/
bash scripts/verify-round.sh rounds/real-r1 # 退出码 0 = 达标
```

- 采样期间保持 3 台以上设备播放；中途加入/退出设备是合法的，N 由窗口内活跃客户端数决定。
- 判据：`verify-round.sh` 退出 0，且偏差 ≤ 10%；输出里同时给出 ratio、N、上限。
- 若返回退出码 2（无效测量），说明设备数不足或埋点不一致，**不计轮次**，修好重跑。
- 需要 iperf3 记录每台 WiFi 实测双向上行时：一端 `iperf3 -s`，另一端 `iperf3 -c <ip> -R`，
  把结果贴进本报告 §7 的表作为实测约束（本机未安装 iperf3，需现场另装）。
